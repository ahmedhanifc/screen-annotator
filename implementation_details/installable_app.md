# Shipping screen-annotator as an installable consumer app

> This is the **phased plan** the work followed (with status notes below). For
> the **as-built reference** — how the tray/hotkey app works and how to build,
> release, and test it — see [`packaging_and_release.md`](packaging_and_release.md).

## Context

Today the tool is a developer-oriented Python package. To *use* it, a person must install
Python + git, run `pip install .`, and then wire up a global hotkey **themselves** —
AutoHotkey on Windows, or `overlay.sh` + a manual desktop-environment keybind on Linux.
There is no background presence and no settings screen. For a non-technical audience that's
three hard barriers before the tool does anything useful.

**Goal:** reduce the barrier to *"download an installer, click Next a few times, press a
hotkey, start drawing."*

**Decided scope:** full consumer experience (installer + tray + built-in hotkey + settings),
**Windows first**, **ship unsigned** for now (document the one-time SmartScreen "Run anyway"
click; code signing can be added later without structural change).

**Package format (decided):** ship the **Inno Setup `.exe`** installer first. MSIX-via-Store
is attractive (Microsoft re-signs Store apps → no SmartScreen) but the *only* free-signing
route is the Store itself (sideloaded MSIX still needs a trusted cert), and this app installs
a **global low-level keyboard hook** + global hotkey — keylogger-like to an automated
reviewer, so it draws extra Store-certification scrutiny and adds a review gate on every
update. The `.exe` works with our global-hook + click-through architecture today. So: `.exe`
now; **MSIX/Store is a documented fast-follow** once behaviour is proven. Phases A–C don't
depend on this choice.

**Icon (decided):** no icon existed; a clean modern marker/pen glyph is generated in-code
(`screen_annotator/icon.py`, `make_app_icon()`), used for the tray + window now, with a
matching `.ico` produced for the exe in Phase C.

**Status:**
- **Phase A** — done. Verified headless (imports + smoke suite + an AppController
  show/hide/shutdown state-machine check) *and* interactively on a live X11 session
  (tray icon, `Ctrl+Alt+A` toggle, pass-through when hidden, tray→Quit).
- **Phase B** — done. Settings dialog edits the **global hotkey** only (tool/colour/size
  already auto-persist as last-used, so explicit default pickers were intentionally
  skipped — can be added later). Hotkey persists to prefs (`"hotkey"` key, merge-on-write
  `save_prefs`) and re-registers live via `AppController.set_hotkey`. First-run tray hint
  added. Verified headless (live re-registration + dialog capture/validation). Interactive
  live check pending.
- **Phase C** — done (authored on Linux; Windows artifact builds on CI). PyInstaller
  one-dir spec `packaging/screen-annotator.spec`; a dedicated `packaging/entry.py`
  (absolute import — `__main__.py`'s relative import fails as a frozen entry script, a bug
  the Linux freeze caught); real multi-size `screen_annotator/assets/icon.ico` (+ `icon.png`)
  generated by `packaging/make_icon.py`; `pyproject` gained a `build` extra (pyinstaller).
  Verified by freezing on Linux and booting the frozen binary through `get_backend`'s
  clean exit (proves the freeze/import/Qt-bundling chain).
- **Phase D** — done (authored on Linux; runs on CI). `packaging/windows/installer.iss`
  (Inno Setup: per-user install = no UAC, MIT licence page, Start-Menu + optional desktop
  shortcut, optional "Launch at login" via HKCU Run, launch-on-finish); `.github/workflows/
  release.yml` (on `v*` tag: PyInstaller + `choco install innosetup` + `iscc`, uploads the
  setup exe as a Release asset; commented `signtool` placeholder); README Download section.
  **Not yet run** — needs a tag push to build on CI, then a Windows VM to verify the
  installer + app interactively.
- **Phase E (Linux AppImage)** — not started.

Three things stack to get there, and the first is a real refactor, not just packaging:

1. **Refactor to a background tray app with a built-in global hotkey** — the core UX unlock.
   The app stops being "launch = overlay, Esc = exit" and becomes a tray icon that registers
   its own global hotkey to **show/hide** the overlay. This deletes the AutoHotkey /
   `overlay.sh` step entirely. Cross-platform (helps Linux immediately too).
2. **Freeze to a standalone binary** (PyInstaller) — removes the Python/git/pip barrier.
3. **Windows installer + auto-build** (Inno Setup wizard, built by CI, attached to a Release).

The Windows pieces cannot be runtime-tested from a Linux box — they ride the existing
`windows-latest` CI + the VM guide in `testing_windows.md`.

## Phase A — Tray app + built-in global hotkey (cross-platform core)

Highest-value, highest-risk change; everything else is packaging around it.

**Lifecycle change (`screen_annotator/app.py`):**
- `app.setQuitOnLastWindowClosed(False)` — hiding the overlay must NOT exit the process.
- Start with the overlay **hidden**. Add a `QSystemTrayIcon` with a menu: *Toggle overlay
  (⟨hotkey⟩)*, *Settings…*, *Quit*, plus a tooltip showing the current hotkey.
- **Show** (hotkey / tray / first-run): clear the canvas, `showFullScreen()` + `raise_()`,
  re-apply click-through (reuse the existing `apply_click_through` + `singleShot(0/300)`
  re-apply dance), `hide_cursor()` + start the cursor poll, and **start the drawing input
  source**.
- **Hide** (what `Esc` / toolbar ✕ now do — repoint `bridge.do_quit`): **stop the drawing
  input source**, `show_cursor()`, `overlay.hide()`. Process stays alive in the tray.
- **Quit** (tray → Quit, or a distinct signal): stop everything and `app.quit()`.

  Why start/stop the drawing input on show/hide: those global button/key grabs are modal and
  must not be held while the overlay is down. Only the *toggle hotkey* stays always-on.

**New always-on toggle-hotkey capability (new method on `PlatformBackend`):**
- Add `make_hotkey_listener(bridge, chord) -> InputSource` to `backends/base.py`. Runs
  independently of the drawing input source and emits a new `bridge.toggle_overlay` signal.
- **Windows (`backends/windows.py`):** a dedicated thread that calls `RegisterHotKey(NULL,
  id, mods, vk)` and runs a `GetMessage` loop catching `WM_HOTKEY`. Reuses the module's
  existing `ctypes`/WinDLL setup and explicit argtypes/restype discipline. Keep it separate
  from the drawing LL-hook thread.
- **Linux (`backends/x11.py`):** a small always-running thread that `XGrabKey`s the chord on
  the **root** window and pumps X events — the module already uses `XGrabKey` for the drawing
  controls, so this is the same technique applied once, globally.

**Bridge (`screen_annotator/bridge.py`):** add `toggle_overlay` and `do_shutdown` signals;
keep `do_quit` but re-wire it in `app.py` to *hide* rather than exit.

**`overlay.sh` / README hotkey sections:** the built-in hotkey supersedes them. Keep
`overlay.sh` as a fallback launcher but demote it in the README; drop the AutoHotkey snippet
in favour of "the hotkey just works, change it in Settings."

**Files:** `app.py` (lifecycle + tray), `bridge.py` (+2 signals), `backends/base.py`
(+abstract method), `backends/x11.py` + `backends/windows.py` (+hotkey listener), a new
`screen_annotator/tray.py` (QSystemTrayIcon + menu), README (hotkey sections).

## Phase B — Settings window (persisted)

- New `screen_annotator/settings.py`: a `QDialog` to set the **global toggle hotkey**
  (key-capture field) and **defaults** (tool, colour, size). Opened from the tray menu and
  on first run.
- Persist via the existing `load_prefs` / `save_prefs` in `config.py` — **extend the schema**
  to include `"hotkey"` (keep the current `tool`/`color_index`/`width`). At startup, read the
  saved hotkey and pass it to `make_hotkey_listener`; changing it re-registers.
- Default hotkey: `Ctrl+Alt+A` (avoids common conflicts; no Super-key assumptions).
- **First run** (no prefs file): show a one-time toast/dialog — "Press ⟨hotkey⟩ anywhere to
  draw. Right-click the tray icon for settings." The friendly on-ramp.
- Per-key remapping of the *drawing* controls (`CONTROL_KEYS` / `MOD_SHORTCUTS`) is a
  **stretch goal** — noted, not built in v1. The tables are centralized in `config.py`, so it
  can be added later by loading overrides from prefs.

**Files:** `settings.py` (new), `config.py` (prefs schema + hotkey default), `tray.py` (wire
the menu item).

## Phase C — Freeze to a Windows binary (PyInstaller)

- Add PyInstaller as a build-time tool (not a runtime dep). A `packaging/` dir with a
  `screen-annotator.spec` (one-dir build; faster startup, and the installer hides the folder
  from users) targeting the tray entry point.
- Ship an **app icon**: add `screen_annotator/assets/icon.ico` (+ a PNG for Linux later) and
  load it for the window + tray + the frozen exe.
- Known caveats to encode in the build/docs:
  - Build **on Windows** — no cross-compile from Linux; use `windows-latest` CI.
  - PyQt6's Qt runtime is bundled by PyInstaller's hooks automatically; verify the GUI
    actually launches in the VM (offscreen CI can't prove that).
  - The Linux clipboard-persistence path shells out to `xclip`; a frozen binary won't include
    it. Not a Windows concern (Qt clipboard is used there), but note it for the Linux phase.

**Files:** `packaging/screen-annotator.spec`, `screen_annotator/assets/icon.ico`, references
in `app.py` / `tray.py` to load the icon.

## Phase D — Windows installer + auto-build/release

- **Inno Setup** script (`packaging/windows/installer.iss`): app metadata + publisher, an
  MIT **license page** (from `LICENSE`), install into `Program Files`, Start-Menu entry,
  **optional desktop shortcut**, **optional "Launch at login"** (Startup-folder shortcut or
  `HKCU\...\Run`), and "Launch now" on finish. Output:
  `screen-annotator-setup-x.y.z.exe`.
- **Release workflow** (`.github/workflows/release.yml`, triggered on a `v*` tag): on
  `windows-latest`, `pip install .` + PyInstaller build, then `choco install innosetup` +
  `iscc installer.iss`, then upload the setup `.exe` as a **GitHub Release asset**. This is
  what a user actually downloads.
- **Signing:** ship unsigned for now. Leave a clearly-commented placeholder step in the
  workflow (`signtool sign ...`) and a README line: users click *More info → Run anyway* on
  the one-time SmartScreen prompt. (Swap in a cert later with no structural change.)
- Keep the existing `ci.yml` smoke matrix as-is (build vs. test separation).
- README: a **Download** section at the top — "Grab the installer from Releases, run it,
  press the hotkey" — ahead of the `pip install` (dev) instructions.

**Files:** `packaging/windows/installer.iss`, `.github/workflows/release.yml`, README
(Download section).

---

## Phase E — Linux packaging (follow-on, after Windows)

- **AppImage** is the Linux equivalent of "download and run": wrap the PyInstaller one-dir
  output with `appimagetool`, ship a `.desktop` file + icon for menu integration. Built on
  `ubuntu-latest` in the release workflow.
- Carry the caveats already true on Linux: **X11 only** (not Wayland), a **compositor** must
  run for transparency, and **`xclip`** is needed for clipboard *persistence* after quit
  (Qt-clipboard fallback works while running). Document these on the download page.
- The built-in hotkey from Phase A already replaces `overlay.sh` for end users; keep
  `overlay.sh` only as a dev/fallback launcher.

**Files:** `packaging/linux/` (AppImage recipe, `.desktop`, icon), release workflow (Linux
job), README.

## Verification

- **Phase A/B on Linux (locally):** run `screen-annotator`; confirm it starts **hidden** with
  a tray icon, the built-in hotkey (`Ctrl+Alt+A`) toggles the overlay show/hide, `Esc`
  **hides** (process survives), drawing input is only grabbed while visible (keys pass through
  to apps when hidden), Settings changes the hotkey and persists across relaunch, and tray →
  Quit fully exits. Extend `tests/test_smoke.py`: assert the new bridge signals exist and that
  `emit_action` + the hotkey chord still round-trip (headless).
- **Phase C/D on Windows (device-free):** the `windows-latest` release job builds the
  PyInstaller exe and the Inno Setup installer as artifacts — proves it freezes and packages.
  Then run the installer in a **VM** (per `testing_windows.md`): wizard screens appear, app
  installs, tray icon shows, hotkey toggles the overlay, "Launch at login" works, uninstall is
  clean, and the SmartScreen "Run anyway" path is as documented.
- **Phase E:** download the AppImage on a fresh X11 Linux session; it runs without a Python
  install; menu entry + icon present.

> Sequencing note: Phase A is a prerequisite for everything and is the only part with real
> design risk (always-on hotkey vs. modal drawing grabs, show/hide vs. spawn/exit). Land and
> verify A on Linux first, then B, before touching the Windows packaging phases.

## Open questions / ambiguities

These are decisions I'd want to confirm (or would otherwise resolve with the noted default)
before or during implementation:

1. **Default toggle hotkey.** Plan assumes `Ctrl+Alt+A`. Is that acceptable, or do you prefer
   something else (e.g. `Ctrl+Alt+D`, or a `Super`-based chord on Linux)? Whatever the
   default, it can conflict with other apps — the Settings remap is the escape hatch.
2. **Tray behaviour when hidden.** Confirm the intended model is *"install once, app lives in
   the tray at login, hotkey toggles the overlay."* The alternative (launch-on-demand, no
   persistent tray) is lower-effort but keeps a launch step. Plan assumes persistent tray.
3. **"Launch at login" default.** Should the installer's *Launch at login* checkbox be
   **ticked or unticked** by default? Auto-start is lowest-friction but more intrusive; plan
   leaves it as an **opt-in (unticked)** checkbox.
4. **Icon / branding.** ✅ Resolved — generate a modern marker/pen glyph. Done in-code as
   `screen_annotator/icon.py::make_app_icon()` (multi-resolution, no binary asset); the
   Windows `.ico` will be rendered from the same drawing in Phase C.
5. **App / publisher name.** The installer shows a "publisher" string and the tray tooltip
   shows a name. Use "screen-annotator" / "Ahmed Hanif"? Confirm the display name and whether
   you want a friendlier title (e.g. "Screen Annotator").
6. **Drawing-key remap scope.** Plan ships settings for the *toggle hotkey + defaults* only;
   full per-key remapping of the drawing controls is deferred. Is toggle-hotkey-only enough
   for v1, or is remapping the drawing keys a must-have now?
7. **Windows single-instance.** Should launching the app while it's already running in the
   tray focus/no-op (recommended) rather than start a second tray icon? Plan assumes a
   single-instance guard, but it adds a little Windows-specific plumbing.
8. **Versioning / release trigger.** Plan triggers releases on a `v*` git tag. Confirm you're
   happy tagging releases manually (vs. building an installer on every push, which is heavier
   and noisier).
9. **Signing timeline.** Shipping unsigned now is decided. Flagging only that the first
   downloads will show SmartScreen's "unknown publisher" prompt until either a cert is bought
   or the unsigned binary accrues reputation — acceptable for launch?
10. **macOS.** Still explicitly out of scope here (roadmap only). The tray + hotkey refactor
    in Phase A is written cross-platform so a future macOS backend slots in, but no macOS
    packaging (.dmg / notarization) is planned in this doc.
